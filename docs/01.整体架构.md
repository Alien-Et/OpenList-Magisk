# 01. 整体架构

## 背景

issue #36 想要 KernelSU 那种热更新入口。热安装只有 KernelSU 有，Magisk / APatch 没法统一；而日常操作（启停、换二进制、改配置、改密码、迁目录）以前都只能进终端。

所以把业务逻辑全收进 `control.sh`，WebUI 只当界面：

- KernelSU / APatch：模块 WebUI
- Magisk：终端执行同一份 `control.sh`
- 三家行为一致，只是入口不同

## 目录结构

```
OpenList-Magisk/
├── module.prop
├── customize.sh          # 安装：选路径、替换占位符、chmod
├── service.sh            # 开机启动、写 module.prop 状态
├── action.sh             # 模块卡片「操作」按钮
├── control.sh            # 统一控制入口（新增）
├── uninstall.sh          # 卸载（动态解析路径）
├── uninstall-user.sh     # 交互式卸载
├── LICENSE               # 模块自身 MIT 许可副本
├── LICENSE-AGPL-3.0.txt  # 上游二进制 AGPL-3.0 全文
├── THIRD-PARTY.md        # 第三方组件与许可说明
└── webroot/              # KernelSU / APatch WebUI（新增）
    ├── index.html
    ├── app.js
    └── style.css
```

## 许可分层

模块自身（脚本 / WebUI / 文档）→ **MIT**；打包进安装包的 `openlist-arm` / `openlist-arm64` / `openlist-amd64` / `openlist-386` → 上游 **AGPL-3.0**（未修改，原样分发）。

这两个许可证互不覆盖：AGPL 的传染范围只到 OpenList 自身，独立进程调用的控制脚本不构成衍生作品。安装包里同时带 `LICENSE`、`LICENSE-AGPL-3.0.txt`、`THIRD-PARTY.md` 三个文件，装到设备上也能直接查。

## 二进制分发策略

四种架构（arm / arm64 / amd64 / 386）各自独立成包，一共 5 个产物、两条更新通道：

| 产物 | 内含二进制 | 更新通道 | 版本号来源 |
|---|---|---|---|
| `openlist-magisk-vX-arm64.zip` | arm64 | `update-arm64.json` | 上游 OpenList |
| `openlist-magisk-vX-arm.zip` | arm | `update-arm.json` | 上游 |
| `openlist-magisk-vX-amd64.zip` | amd64 | `update-amd64.json` | 上游 |
| `openlist-magisk-vX-386.zip` | 386 | `update-386.json` | 上游 |
| `openlist-magisk-online.zip` | 无 | `update.json`（仓库根） | 独立维护 |

**一个包只装一个架构的二进制**，不再有「双架构包」或「四合一 full 包」——一个设备只需要一份，多塞的只是浪费。

版本号分流是这套设计的核心：

- 架构包由 `1.yml` 跟着上游 OpenList 自动构建，`version` / `versionCode` 来自上游 Release
- online 包由 `online.yml` 手动触发构建，版本号自己填
- 仓库里的 `module.prop` 只是**模板**，打包时用 `sed` 生成临时副本注入各包自己的版本号与 `updateJson`，**仓库文件从头到尾不改** —— 一份 `module.prop` 装不下两套版本号，所以干脆不装

`customize.sh` 取二进制走四级回退：

1. 包内 `$MODROOT/openlist-<arch>`
2. `/sdcard/Download/openlist-android-<arch>.tar.gz`（离线兜底，TWRP 刷机靠这条）
3. `control.sh fetch-bin <arch> <版本>` —— 复用镜像列表与 md5 校验，走 `releases/download/vX.Y.Z/` 固定路径，不耗 API 额度，下载的版本与模块版本严格一致
4. 全失败 → `abort` + 打印手动下载地址

`fetch-bin` 复用 `control.sh` 已有的 `http_download`（直连 → 15 个国内镜像依次试）和 `mirror_ranking`。安装期置 `NO_RANK=1` 跳过并发测速，省 8 秒等待。

## 两条更新通道为什么不打架

模块管理器检查更新时，读的是**已安装模块** `module.prop` 里的 `updateJson`。所以：

- 4 个架构 packages 内嵌 `.../main/update-<arch>.json`
- online 包内嵌 `.../main/update.json`

两个地址都是仓库 `main` 分支的 raw 链接，**不用 `releases/latest/`**。原因：`latest` 指向最新那个 Release，上游发版会把它抢走，那时 `update-arm64.json` 就不在 latest 指向的 Release 里，四架构用户检查更新全是 404。

`update.json` 的 `zipUrl` 直接指向该版本 Release 里的 online 包（`releases/download/vX.Y.Z/openlist-magisk-online.zip`），同样不用 latest。

## 分层

```
webroot/index.html + app.js        (KernelSU / APatch)
        │ ksu.exec
        ▼
control.sh                         (root CLI，唯一事实来源)
   ├── status / start / stop / restart
   ├── check / update
   ├── fetch-bin              (安装期取二进制)
   ├── logs
   ├── config-get / config-save
   ├── passwd / token / api
   ├── migrate-data / migrate-bin / fix-paths
   └── version
        │
        ├── service.sh   (启动 openlist、写 module.prop)
        ├── action.sh    (模块卡片按钮)
        └── OpenList API (127.0.0.1:端口)
```

约束：

- WebUI 不承载业务判断，只传参、校验、渲染。
- `control.sh` 不依赖 WebUI，任何终端都能调用。
- `action.sh` 保留，作为 Magisk 的唯一入口。

## 兼容性

| 管理器 | WebUI | control.sh | 模块卡片按钮 |
|---|---|---|---|
| KernelSU | ✅ | ✅ | ✅ |
| APatch | ✅ | ✅ | ✅ |
| Magisk | ❌（无 webroot） | ✅ | ✅ |

## 数据流

1. **状态**：`pgrep` + `ss/netstat` + `config.json` + `module.prop`
2. **启停**：`control.sh` → `service.sh` 或 `pkill`
3. **更新**：GitHub Release → 下载 → 校验 → 替换 → 启动 → 同步版本（长任务走 `update-bg` 后台跑）
4. **管理操作**：`control.sh api` → OpenList 管理 API（需要 admin token）
5. **配置**：`offline.conf`（下载配置）+ `config.json`（启动配置）
