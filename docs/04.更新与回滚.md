# 04. 更新与回滚

## 版本信息从哪来

```
GET https://api.github.com/repos/OpenListTeam/OpenList/releases/latest
```

模块只认这四个 Android 资产：

| 资产 | 架构 |
|---|---|
| `OpenList-android-arm64.tar.gz` | arm64-v8a |
| `OpenList-android-arm.tar.gz` | armeabi-v7a / armeabi |
| `OpenList-android-amd64.tar.gz` | x86_64 |
| `OpenList-android-386.tar.gz` | x86 |

架构用 `ro.product.cpu.abi` 判断，取不到就当 arm64。`md5-android.txt` 的格式是 `hash  ./文件名`。

## 检查更新与版本列表

`check` / `versions` 只走官方 API，不套镜像——国内那批镜像都不转发 `api.github.com`，套上去只会多一层 403。

- `versions` 用 `per_page=100` 一页页翻到底，`tag_name` 和 `published_at` 按顺序配对，draft 靠「新 TAG 覆盖旧 TAG」自愈
- 只保留 `^v[0-9]` 的 tag，`beta` 这类分支 tag 不进列表
- 结果缓存 5 分钟，省着点用那 60 次/小时的未认证额度
- 403 会分开说「限流」还是「拒绝访问」，并把响应体前 160 字塞进 `debug=`
- 想提额度就把 PAT 写进 `<模块目录>/.github_token`，一行就够

## 没代理的时候

国内直连 `api.github.com` 经常不通，但 `github.com` 上的下载资源走镜像没问题，所以两条链路是分开的：

| 步骤 | 依赖 | 挂了怎么办 |
|---|---|---|
| 版本列表 / 最新版本 | `api.github.com` | 用上次成功的缓存，带 `stale=1`，界面上标「离线缓存」 |
| 下载二进制 | `github.com/.../releases/download/...` | 直连 → 按实测延迟排序的镜像 |
| 指定版本安装 | 不需要 API | 直接拼 `releases/download/<tag>/<asset>` |

`update --tag vX.Y.Z` 是给回退和切版本用的，它压根不查 API，所以断网也能用。

## 下载镜像

偏好存在 `<数据目录>/mirror.conf`：

```
mode=auto      # auto / direct / custom
url=           # mode=custom 时生效，形如 https://ghfast.top/
```

| mode | 行为 |
|---|---|
| `auto` | 直连 → 全部镜像按实测延迟从快到慢依次试（排序缓存 30 分钟） |
| `direct` | 只直连 |
| `custom` | 先试你指定的镜像，不行再按实测顺序兜底 |

15 个镜像都在候选池里，`mirror-ping` 并发测一遍，探针是
`releases/latest/download/md5-android.txt`（几百字节，不绑版本），返回 200/206/3xx 才算活。
排序写到 `<数据目录>/.mirror_rank`，`mirror-rank` 可以直接看当前顺序。

选镜像不影响版本列表——那还是 `api.github.com` 的事。

## 下载与校验

- 下载优先 `curl`，没有就 busybox `wget`
- 先下 `md5-android.txt`，按文件名取 md5 对比；对不上直接中止，不动现有二进制
- md5 文件缺失就跳过校验（官方偶尔不带），不阻断更新
- 下载期间每 2 秒把已下载大小写进 progress 文件，WebUI 显示「N MB」

## 为什么更新要后台跑

宿主（KernelSU / APatch 的 WebUI）执行 `ksu.exec` 时，调用一返回或超时，同一进程组的子进程会被一起收走。同步跑 `update` 要几分钟到几十分钟，中途被掐就只剩一句「更新失败」，连输出都没有。

所以拆成两段：

| 命令 | 干什么 |
|---|---|
| `update-bg --force [--tag vX.Y.Z]` | 用 `setsid` 起独立会话跑真正的 `update`，立刻返回 `running=1` |
| `update-status` | 轮询：还在跑就回 `stage`/`detail`；跑完回 `done=1` 加子进程的 `result=` / `error=` |

结果文件都在 `/data/local/tmp/`：`OpenList_update.out`、`.done`、`.running`。
进程被系统杀掉时会明确说「更新进程已退出但没有结果」，不会又变成一句空错误。

## 替换流程

```
pkill -f "$BIN server"
  → 等 10×0.5s，超时补 pkill -9
  → 备份 $BIN 到 $BIN.bak
  → 新文件先写 $BIN.new（同目录，rename 才是原子的）
  → chmod 755 + mv -f 覆盖
  → 目标是 /system/bin 时补 chcon system_file
  → 重新拉起，轮询 15 秒看进程在不在
```

## 启动失败就回滚

1. `cp $BIN.bak $BIN`，`chmod 755`
2. 重新拉起旧版本
3. 输出 `rolled_back=1`、`result=fail`、`error=新版本启动失败，已回滚到 x.y.z`
4. `module.prop` 的版本号保持原样——宁可显示旧版本，也不要写一个跑不起来的新版本号

## 版本号规则

```
架构包：  versionCode = 主版本×10000  + 次版本×100 + 修订号
          v4.2.10 → 40210    v4.2.11 → 40211    v4.10.0 → 41000

online：  version     = 日期 + 当日流水号，形如 2026.11.24-1（次日归零）
          versionCode = Unix 日数×100 + (流水号 - 1)
          2026.11.24-1 → 2078100    2026.11.24-2 → 2078101
          2026.11.25-1 → 2078200
```

架构包用 10000 当主版本权重，是为了让次版本到两位数时不撞号（旧公式 `×1000 + ×100` 下，`v4.10.0` 和 `v5.0.0` 都算成 5000）。代价是次版本、修订号都得小于 100。

online 用「日数×100 + 流水号」，两个目的：跨天时 `2078200 > 2078102`，天然递增；同一天内靠流水号拉开。`int32` 能容纳 2147 万天（约 6 万年），实际不会溢出。

发布时**只填 8 位日期**（如 `20261124`），流水号由 `online.yml` 读 `update.json` 里的上一版自动 +1 —— 同一天发第几版不需要人记，也就不会因为忘记改号而撞号（撞号会导致用户收不到更新提示）。

online **不能**挂上游版本号（例如 `v4.2.10-online`）：本包不含二进制，安装时下载的是上游 latest，写死某个上游版本就是假信息。所以两条通道的版本号彻底解绑，各自占一个 Release。

**两套版本号各走各的：**

| | 架构包（`OpenList(binary)`） | online 包（`OpenList(online)`） |
|---|---|---|
| 版本号来源 | 上游 OpenList Release，CI 自动同步 | 日期 + 当日流水号，发布时只填日期 |
| 写进哪里 | `update-<arch>.json` + **包内** `module.prop` | `update.json` + 包内 `module.prop` |
| 仓库里的 `module.prop` | **不改**（它只是模板） | **不改** |
| 更新日志 | 上游 Release body → `OpenList-Magisk/CHANGELOG.md` | `CHANGELOG-ONLINE.md` |

`update` 换完二进制后，**只有架构包通道**才把 `module.prop` 的版本改成新 tag 对应的值 —— 它的模块版本本来就等于二进制版本。**纯在线包通道不动 `module.prop`**，它的版本号是模块自身的日期版本（如 `2026.11.24-1`），被二进制版本顶掉就废了。判断依据是 `module.prop` 里的 `channel=binary|online`，老包没有这行时按 `updateJson` 指向哪份清单推断。

两条通道都会把二进制版本单独写进 `.bin_version`，**模块目录和数据目录各一份**（模块目录每次升级都会被整体替换，
只放那里的话升级后必定丢）。WebUI 的「OpenList 版本」先读模块目录、再读数据目录，
两份都没有才去问二进制自己（依次试 `version` / `--version` / `-v`）；服务启动成功时 `service.sh` 也会补写一次。
启动失败自动用 `.bak` 回滚，版本号不动。

## 已知限制

- 没有断点续传，断了就重下
- 不检查剩余空间（arm64 包约 165MB，解压再占一份）
- 镜像全挂且直连不通时，确实更新不了——这时候用 `--tag` 也救不了，得先解决网络
